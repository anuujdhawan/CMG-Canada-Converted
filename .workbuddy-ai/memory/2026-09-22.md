## Reusable method: diagnosing "Discovered - currently not indexed"

1. Read the GSC drilldown; note `Last crawled` — epoch 0 means *never crawled*, which points
   at crawlability/linking, not content quality.
2. Fetch the live sitemap and diff it against the reported URLs.
3. Crawl every sitemap URL with a Googlebot UA, strip `<script>`/`<style>`, and build the
   inbound-link graph from the static HTML only. Compare avg inbound links for indexed vs
   unindexed pages — a large gap identifies the cause immediately.
4. Only then look at content: word counts, duplicate titles/descriptions, and shingle
   similarity **after** dropping shingles that appear on >25% of pages (otherwise shared
   header/footer/CTA text makes everything look duplicated).

## Gotchas

- Any nav rendered conditionally on client state (`{open && …}`) is invisible to crawlers.
  Hide with CSS/`inert`, never unmount, when the links matter for SEO.
- `inert` is safe on `motion.div` — React 19 renders `inert=""`/omits it, and framer-motion
  forwards non-motion props through to the DOM.

## Fix: `npm run dev` panics with `Symlink [project]/node_modules/node_modules is invalid`

A stray symlink `node_modules/node_modules` → `~/.cache/codex-runtimes/codex-primary-runtime/
dependencies/node/node_modules` made Turbopack panic on every endpoint write
(`Failed to write page endpoint /_app`, `Failed to write app endpoint /page`). Fixed with
`unlink node_modules/node_modules`.

- Cause: the artifact-tool runtime symlinks its own deps into the project's `node_modules`
  when scripts run with cwd = project root. A directory literally named `node_modules` inside
  `node_modules` is what `find_package` chokes on.
- `node_modules/@oai` → the same cache dir was left alone: root-level scratch `.mjs` scripts
  (`mark_*.mjs`, `verify_*.mjs`) import `@oai/artifact-tool`, and Turbopack only trips on
  package-named dirs, not scope dirs. Don't delete it — those scripts break.
- If it ever recurs, `next dev --webpack` (what `npm run build` already uses) bypasses
  Turbopack entirely. To audit: `find node_modules -type l` and check for absolute targets.

## Gotcha: openpyxl formulas show blank in previewers, and there is no LibreOffice here

`recalc.py` fails in this environment: no LibreOffice (`/Applications` has none) and the
`formulas` package is not installed — and the skill forbids `--allow-install` without explicit
user authorisation. openpyxl also writes formulas with an **empty `<v />` placeholder**, so
pandas / `data_only=True` / mail previews render them blank.

**Workaround used** (`.guest-post-sites.ref/patch_cache.py`, reusable): compute the formula
results in Python at build time, dump them to `cached.json`, then rewrite the xlsx zip and
regex-replace the `<v />` after each `<f>…</f>` with the real value:

```python
pat = re.compile(r'(<c r="%s"(?:[^>]*?)>)(<f>.*?</f>)(?:<v\s*/>)?(</c>)' % re.escape(ref))
```

Formulas stay live for Excel/WPS; previewers get values. Two traps: resolve the sheet's
`rId` → file path by parsing **each `<Relationship>` tag separately** (attribute order is not
guaranteed, so a single combined regex KeyErrors), and match the `<v />` placeholder or the
substitution silently no-ops. All cached values must be numeric — string results would need
`t="str"`.

### Follow-up: the same pack as a single Word file

User asked for all 111 articles **plus their backlink details in one .docx**.
`outputs/backlink-articles/Commonwealth-Migration-Backlink-Articles.docx` (208 KB) —
1 title, 16 H2 sections, 111 H3 articles, 434 H4 subheadings, 75,229 words.

**Route:** `tencent-docs-routing` → **`tencent-local-office-edit`**, deliberately *not*
`tencent-docx`. The docx pipeline regenerates content through doc-writer/doc-formatter, which
would have rewritten the 111 articles; the routing rule for "source material turned into a

**How it was built:** `build-word.mjs` writes `word/chunk-00.md` (title + how-to + the 111-row

anchors extracted by regexing the body for `[anchor](url)` and taking first/last. Then
`create_doc` → 15 × `doc_insert_markdown` with `markdown="file://<abs path>"` (the `file://`
form makes the server read the file rather than passing 36 KB inline), chaining each call on the
returned `last_edit_index` → `save_file` with the real `file_path`.

**Verified by unzipping the docx, not by trusting the tool's success message:** 222 HYPERLINK
field codes (111 URLs × exactly 2), 1 table at 112 rows × 4 cols, 562 `w:outlineLvl` paragraphs
matching the outline, all XML parts well-formed.

**Gotchas that would have looked like failures:**

- Markdown links land as **HYPERLINK field codes** (`w:fldChar` + `w:instrText`), not
  `w:hyperlink` elements — grepping for `w:hyperlink` returns 0 and proves nothing.
- Headings land as **`w:outlineLvl` + direct formatting**, not `w:pStyle="HeadingN"`, so grepping
  for `Heading` finds nothing. `doc_get_outline` is the real check, and it returns `{items:[…]}`

- URLs inside `w:instrText` are HTML-escaped as `&quot;…&quot;`; split on `&quot;`, not `"`.
- `edsdk.py schema doc_apply_named_style` throws `'list' object has no attribute 'get'` — the
  tool is unusable, and the skill forbids guessing params without a schema, so headings stayed on
  outline levels. That is fine: Word's nav pane and `TOC \o "1-3"` both honour outline levels.
- `doc_list_tables` returns `{tables:[…]}`; rows/cols must be derived from `editable_cells`.

**2. `src/styles/globals.css` — the CTA overhang. I first "fixed" this and was wrong.**

`body:has(.cmg-template-home) .site-header__nav-shell .site-header__cta` carried
`transform: translateX(3.25rem)` (52px). I read it as an accident and replaced it with
`transform: none`. **The user corrected me: the overhang is deliberate** — the button is meant to
sit ~65–75% inside the pill with the rest hanging outside.

Replaced the magic 52px with a proportional offset that holds the split at any button width:

```css
transform: translateX(calc(30% + 15px));   /* 70% in, 30% out */
```

- The `15px` is the shell's own inset (1px border + 14px padding), so the 30% is measured from the
  pill's **visible border**, not its content box: `(15 - t + W)/W = 0.70` exactly.
- `translateX(%)` resolves against the element's own width, so the *fraction* survives a label or
  font-size change. The old 52px only hit 74.7% because the button happened to be 146px wide.
- Hover: `translateX(calc(30% + 15px)) translateY(-2px)` — the original hover re-stated the same
  X, which is what made the offset look baked-in.

Measured after, across 1120→1680px: `insidePill 70.0%`, `outsidePill 30.0%`, overhang 44px at
every width. 70% is the middle of the stated 65–75% band.

**Not changed (flagged to the user instead):** at ≤1252px the shell is no longer at its 1220px max
and only ~16px of room exists past the pill, so the 44px overhang is clipped by the viewport
edge (28px clipped at 1120px, 14px at 1280px, 0 at ≥1366px). Pre-existing — the old 52px clipped
21px at 1120px — and harmless for scrollbars because `.site-header` is `position: fixed`, so fixed
overflow never reaches the document scroll area. A `max-width: 1323px` media query setting
`transform: none` would remove it; left out pending the user's call.

**Also pre-existing, flagged not fixed:** on `/immigrate/express-entry` both **Immigrate and Tools**
get the red active pill, because `isActiveNavItem` counts any *descendant link* — and the Tools
menu's "Learn & prepare" column contains "Express Entry Guide" → `/immigrate/express-entry`.
Confirmed byte-identical before and after my change.
