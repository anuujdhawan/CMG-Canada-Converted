## Pinwheel logo re-applied to the favicon set (SERP + browser tab)

The user handed over `WhatsApp Image 2026-09-24 at 22.47.30.jpeg` (640×640, red pinwheel on
white) and asked for it applied to **Google SERP results and the browser-tab title bar**.

### The honest finding, stated first

**The icon already was this artwork.** `public/images/favicon_LG.webp` (1280×1280) is the same
pinwheel at the same 70.9% framing — verified pixel-equivalent to the supplied JPEG apart from
compression noise (mean abs channel diff **1.98/255**). So this was not a missing logo; it was a
re-generation, and the real defects were elsewhere:

1. All three icons were **opaque white-backed** (`icon.png` and `apple-icon.png` carried an alpha
   channel whose every pixel was 255). On any dark browser chrome or in Google's dark SERP the tab
   icon rendered as a **white square**.
2. The mark only filled **70.9%** of the tile — ~11px of actual mark at 16px.

### What changed

New generator `scripts/build-brand-icons.mjs`, wired as **`npm run build:icons`**.

| File | Before | After |
|---|---|---|
| `src/app/favicon.ico` | 16/32/48/64 RGBA, opaque white | same sizes, **transparent**, 9.2 KB |
| `src/app/icon.png` | 192×192, opaque white | 192×192, **transparent**, 14.6 KB |
| `src/app/apple-icon.png` | 180×180, opaque white | 180×180, **still opaque on white** — deliberate, see below |

- Alpha recovered from the **green channel** (`a = (255-g)/(255-40)`), then every pixel forced to
  the logo's own red. Strips the compression noise a naive white→transparent would keep.
- Re-framed to **88%** fill. Single-step `lanczos3` beat both stepped and pre-blur downscaling at
  16px (pre-blur was catastrophic — the mark nearly vanished).
- **`apple-icon.png` stays opaque on white**: iOS composites a transparent touch icon onto black,
  so transparency there would produce a black home-screen tile.
- ICO is hand-assembled (sharp cannot write ICO) with PNG payloads at 32bpp.

### The colour decision

The artwork's red is **`#D02818`**, not the CSS `--brand-primary` **`#D80621`**. Sampled all four
brand assets to confirm: the pinwheel, `CMG-LOGO.webp` (header wordmark) and the footer bird are
*all* `#D02818`. **The logo red was preserved — the icon was not snapped to the UI token.**

## Follow-up: "will Google actually pick it up?" — end-to-end verification

The user pushed back on the earlier "not verified" caveat. Correct instinct — the build could not
run, but that turned out not to mean the head was unverifiable.

### How it was actually verified

`lsof -nP -iTCP -sTCP:LISTEN` showed the user's own **`next dev` running on port 3000** (and a
second app on 3005). That is the real metadata code path, so the head was read straight off it:

```
<link rel="icon" href="/favicon.ico?favicon.3nf_6xi395tmb.ico" sizes="128x128" type="image/x-icon"/>
<link rel="icon" href="/icon.png?icon.1jv6bghqk_ns7.png"      sizes="192x192" type="image/png"/>
<link rel="apple-touch-icon" href="/apple-icon.png?…"          sizes="180x180" type="image/png"/>
```

All three URLs → HTTP 200, correct `Content-Type`, and **byte-identical (`cmp`) to the new files**.
Also checked: `/favicon.ico` with **no** query → 200 (Google's classic fallback); a stale hash → 200;
`robots.txt` → `Allow: /` with no `Disallow`; `next.config.mjs` has no `headers()` so no
`X-Robots-Tag`; `buildMetadata()` in `src/lib/seo.js` does not touch icons; only one `layout.js`
exists, so nothing overrides them; no `public/favicon.ico` shadowing.

### The real defect this found — ICO entry order

The **live** site was advertising `sizes="16x16"` for its favicon. Root cause:
`getImageSize()` (`next/dist/server/image-optimizer.js`) returns the **first** ICO directory entry,
not the largest. Ascending order — the conventional way to write an ICO — therefore reports 16×16.
Confirmed by rebuilding the container in both orders:

| order | `getImageSize` |
|---|---|
| `16/32/48/64` | `16x16` |
| `64/48/32/16` | `64x64` |

**Fixed:** `buildIco` now sorts descending and the set is `128/64/48/32/16`, so Next declares
`sizes="128x128"`. Verified after the change: all five entries decode as square PNGs with real
transparency, and the dev server emitted `sizes="128x128"` with bytes matching disk.

### Why the `?<hash>` query is not a problem

`next-metadata-image-loader.js` L60 uses webpack's **`[contenthash]`**, i.e. derived from file
content — so it is stable across deploys and only changes when the icon changes. Google's "favicon
URL must be stable" rule is satisfied. The live production site was also fetched and compared:
it currently serves the **old opaque-white** 192px `icon.png`, so the deploy will visibly change it.

### Honest residual risk (told to the user)

Google's doc says a favicon is **not guaranteed** to appear even when every guideline is met, and
recrawling the home page takes **days to weeks**. Recommend Search Console → URL Inspection →
Request Indexing on `/`. Unverifiable from here: whether the production host or its CDN blocks
query-string or `.ico` requests. Not a defect in the repo.

Note: `getImageSize` on this project's Next returns `16x16` for an ascending ICO, but the running
dev server reported `64x64` for the same file — a dev-server caching artefact that was never fully
explained. It does not affect a clean production build, and the post-fix reading (128x128) matched
the file exactly.
